LC STATE ENCODING REFERENCE
================================================================================

Life Cycle State Encodings (4-bit raw values, differentially encoded to 8 bits in eFuse OTP) - per OCAH SPEC 2026-02-02:
  Differential encoding: {~raw[3:0], raw[3:0]} = 8 bits

  State Name        | Raw Encoding | Diff Encoded   | Description
  ------------------|--------------|----------------|------------------------------------------
  TEST_DEV          | 4'b0000      | 8'hF0          | Test/Development state (default)
  PROD              | 4'b0001      | 8'hE1          | Production state
  PROD_DBG          | 4'b0001*     | 8'hE1*         | Production Debug (PROD + DEMOTE_1 or DEMOTE_2=1; two flavours, see below)
  RMA_SIP           | 4'b001X      | 8'hD2 or 8'hC3 | RMA System-in-Package (0x2 or 0x3)
  RMA_CHIPLET       | 4'b011X      | 8'h96 or 8'h87 | RMA Chiplet level (0x6-0x7)
  PROD_END          | 4'b1000      | 8'h78          | Production End (terminal state; no transitions except to INVALID)
  INVALID           | 0x4-0x5,0x9-0xF | various     | Invalid state (error fallback, EOL)

  Note: RMA state transitions require token matching authorization in eFuse
        controller (see SEP_EFUSE_TEST_PLAN.txt Suite 6).
        RMA_CHIPLET entry: from RMA_SIP (with RMA_CHIPLET_TOKEN) or
        from TEST_DEV (with BOTH RMA_SIP_TOKEN AND RMA_CHIPLET_TOKEN match).
        PROD → RMA_CHIPLET direct is NOT allowed.

  *Note: PROD_DBG is not a separate encoding - it is PROD state (4'b0001, encoded 8'hE1) with
         DEMOTE_1 or DEMOTE_2 CSR bit set to 1. Two flavours (per OCAH spec March 5th):
         - PROD_DBG_1: BL1 firmware uses DEMOTE_1 + DEMOTE_LOCK_1 → full debug access
         - PROD_DBG_2: BL2 firmware uses DEMOTE_2 + DEMOTE_LOCK_2 → restricted access
         Both pairs (DEMOTE_1/2, DEMOTE_LOCK_1/2) are volatile and clear on cold reset.

Security Domains (per OCAH spec March 5th — TWO domains):
  - Domain 1: Controls debug access to LOCAL assets (BL1 firmware, DEMOTE_1)
  - Domain 2: Controls debug access to DOWNSTREAM chiplets (BL2/SIP firmware, DEMOTE_2)

State Transition Rules (updated per OCAH spec March 5th):
  - TEST_DEV → PROD, PROD_END, RMA_SIP, RMA_CHIPLET
  - PROD → RMA_SIP (NOT directly to RMA_CHIPLET or PROD_END)
  - PROD ↔ PROD_DBG_1/2 (via DEMOTE_1/2 CSR, no eFuse change)
  - RMA_SIP → RMA_CHIPLET (with RMA_CHIPLET_TOKEN)
  - PROD_END is terminal (no transitions out); entered only from TEST_DEV
  - RMA_CHIPLET is terminal (no transitions out)
  - INVALID is error state (requires cold reset recovery)

  RMA_CHIPLET entry rules:
    - From TEST_DEV: Direct with BOTH RMA_SIP_TOKEN AND RMA_CHIPLET_TOKEN match
    - From RMA_SIP: With RMA_CHIPLET_TOKEN (sequential from PROD)
    - From PROD: BLOCKED (must go through RMA_SIP first)

  Note: Transitions to RMA states require token authorization in eFuse
        (see SEP_EFUSE_TEST_PLAN.txt Suite 6).
        LCC reads authorized state from eFuse shadow registers after reset.

FEATURE CONTROL VECTOR BIT DEFINITIONS
================================================================================

Feature control vectors: SIP_DIS, SYS_DIS (per spec March 5th)
Feature control is a function of LC_STATE and DIS vectors
Note: CHP_DIS struck through in OCAH spec v0.86 — only SIP_DIS and SYS_DIS used in RTL

Bit Field Layout (applies to each 64-bit DIS vector) - per OCAH SPEC 2026-02-02:

  Bit Range | Field Name    | Description
  ----------|---------------|--------------------------------------------
  [4:0]     | Debug         | Debug feature disable bits
            |   [0]         | SEP_DBG: SEP debug access
            |   [1]         | SOC_DBG: SoC debug access
            |   [2]         | AP_DBG: Application Processor debug
            |   [3]         | AP_TRACE: AP trace functionality
            |   [4]         | SIP_DBG: External debug not forwarded to outbound JTAG PTAP
  ----------|---------------|--------------------------------------------
  [31:5]    | (reserved)    | Reserved for future debug features
  ----------|---------------|--------------------------------------------
  32-36     | Test          | Test mode disable bits (individual bits)
            |   [32]        | FUSE_TEST: eFuse test mode
            |   [33]        | SEP_STEST: SEP screening test
            |   [34]        | SEP_DTEST: SEP diagnostic test
            |   [35]        | AP_STEST: AP screening test
            |   [36]        | AP_DTEST: Diagnostic tests for non-SEP logic
  ----------|---------------|--------------------------------------------
  [47:37]   | (reserved)    | Reserved for future test features
  ----------|---------------|--------------------------------------------
  [63:48]   | Function      | Functional feature disable bits
            |   [48]        | Feature-specific (implementation defined)
            |   [49-63]     | Additional functional features
  ----------|---------------|--------------------------------------------

  Feature Control Per LC State (per OCAH spec March 5th):
  SEC_DIS == False (1'b0):

  LC State      | Debug [4:0]           | DFT (bits 32-36)      | Function [63:48]
  --------------|----------------------|-----------------------|-------------------
  TEST_DEV      | ~(SIP|SYS).DBG       | ~(SIP|SYS).DFT        | ~(SIP|SYS).FUNC
  PROD          | All disabled (F)     | All disabled (F)      | ~(SIP|SYS).FUNC
  PROD_DBG_1    | All enabled (T)      | All disabled (F)      | ~SIP.FUNC
  PROD_DBG_2    | All enabled (T)      | All disabled (F)      | ~SYS.FUNC
  PROD_END      | All disabled (F)     | All disabled (F)      | ~(SIP|SYS).FUNC
  RMA_SIP       | ~SIP_DIS             | ~SIP_DIS              | ~SIP_DIS
  RMA_CHIPLET   | All enabled (T)      | All enabled (T)       | All enabled (T)
  INVALID       | All disabled (F)     | All disabled (F)      | All disabled (F)

  SEC_DIS == True (1'b1):
  All states: {T, T, T} - "Fully open device independent of LC state" (per spec)

Note: SIP = SIP_DIS, SYS = SYS_DIS
      ~ = bitwise NOT, | = bitwise OR
      CHP_DIS struck through in OCAH spec v0.86 — only SIP_DIS and SYS_DIS used in RTL

PROD_DBG_1/2 Feature Control (per OCAH spec March 5th):
  - PROD_DBG_1 (via DEMOTE_1): Debug=T, DFT=F, Func=~SIP_DIS.FUNC
    Full debug access; chiplet owner (BL1) controls
  - PROD_DBG_2 (via DEMOTE_2): Debug=T, DFT=F, Func=~SYS_DIS.FUNC
    Full debug access; SIP owner (BL2) controls
  - DEMOTE_1/2 also enable all debug features in TEST_DEV and RMA_CHIPLET
  - "The user has the freedom to determine how these demotion register
    facilities are used and there are no hard-coded restrictions"

SEC_DIS Override:
  - When sec_dis signal from eFuse asserts (token matching in eFuse scope):
    * {T, T, T} - All features enabled, "independent of LC state" (per spec)
    * This includes INVALID state (spec does not exempt it)
  - Note: SEC_DIS token matching performed in eFuse controller
          (see SEP_EFUSE_TEST_PLAN.txt Suite 6)

SIP INTEGRATION CONTEXT
================================================================================

This section explains the architectural rationale for OCAH's two-domain
lifecycle control approach, driven by System-in-Package (SiP) integration
requirements from the OCAH specification Section 4.6.2.

Background: Secure Lifecycle Control in SiP
--------------------------------------------

In SiP (System-in-Package) integration scenarios, chiplets often have security
assets that belong only to the chiplet designers (not the SiP integrator). This
creates a need for **distributed secure lifecycle control** - each chiplet must
maintain its own security domains while participating in a shared package-level
security architecture.

Challenge 1: Misaligned Lifecycle States
-----------------------------------------

Different chiplets in a SiP may have different lifecycle states at any given
time due to:
  - Independent manufacturing and testing flows
  - Different security policies (chiplet-level vs package-level)
  - Asynchronous lifecycle transitions

**Consequences of misalignment**:
  1. Inconsistent debug/test access across chiplets
  2. Divergent key derivation (keys derived from different LC states)
  3. Security policy conflicts at package boundaries

Challenge 2: Misaligned Lifecycle Control Schemes
--------------------------------------------------

Chiplets may implement different granularities of lifecycle control:
  - Some chiplets: Coarse lifecycle (e.g., TEST, PROD, RMA only)
  - Other chiplets: Fine-grained lifecycle (e.g., TEST_DEV, PROD, PROD_DBG, PROD_END, RMA_SIP, RMA_CHIPLET)
  - Package integrator: May require additional package-level states

**Consequences of misalignment**:
  1. Cannot enforce uniform security policies across package
  2. Difficult to coordinate multi-chiplet debug/test operations
  3. Incompatible RMA (Return Merchandise Authorization) flows

OCAH Solution: Two-Domain Security Architecture
-----------------------------------------

OCAH addresses these challenges with a **2-domain security architecture** (per spec March 5th):

  Domain 1: Controls debug access to LOCAL assets
    - BL1 firmware controls DEMOTE_1 / DEMOTE_LOCK_1
    - Feature control uses SIP_DIS for PROD_DBG_1
    - Chiplet-local security resources

  Domain 2: Controls debug access to DOWNSTREAM chiplets
    - BL2/SIP firmware controls DEMOTE_2 / DEMOTE_LOCK_2
    - Feature control uses SYS_DIS for PROD_DBG_2
    - Inter-chiplet security resources

The final feature control vector uses the DIS vectors (per spec March 5th):
  feature_disable_o = f(LC_STATE, SIP_DIS, SYS_DIS)
  Note: CHP_DIS struck through in OCAH spec v0.86 — only SIP_DIS and SYS_DIS used

This ensures that any domain can disable features for security, but no single
domain can unilaterally enable features (defense in depth).

Security Requirements (from OCAH Spec)
---------------------------------------

**[OPT-SEC-1]**: SiP Integration Best Practice
  - SiP integrators SHOULD only expose chiplets that have sufficient secure
    lifecycle control protection for security assets
  - Rationale: Prevents integration of insecure chiplets into security-critical packages

**[REQ-SEC-6]**: Debug/Test Traffic Forwarding Control
  - Chiplets that forward debug/test traffic between themselves and other
    chiplets MUST provide access control mechanisms
  - Access control MUST protect BOTH:
    1. Local chiplet debug/test resources
    2. Debug/test traffic forwarded to other chiplets
  - The lifecycle control policy for forwarded traffic MUST be controlled by
    the SiP integrator (not local to the forwarding chiplet)
  - Rationale: Prevents a compromised chiplet from enabling debug access to
    other chiplets in the package

**[REQ-SEC-7]**: Shared Security Domain Lifecycle Control
  - For chiplets in a **Shared Security Domain** (security boundaries span
    multiple chiplets), the lifecycle control policy MUST be controlled by the
    SiP integrator only
  - Local chiplet designers MUST NOT have unilateral control over lifecycle
    policies that affect security assets shared across chiplets
  - Rationale: Ensures consistent security policies across shared security boundaries

Note on Security Domain Types:
  - **Local Security Domains**: Implementation-defined, controlled by chiplet
    designer (e.g., chiplet-local crypto keys, chiplet-local debug resources)
  - **Shared Security Domains**: Controlled by SiP integrator (e.g., inter-chiplet
    secure communication, package-level root-of-trust, shared debug infrastructure)

Impact on LCC Verification
---------------------------

These SiP integration requirements drive the following verification priorities:

1. **Two-Domain Feature Control (TEST 2.4, 3.2)**: Verify that Domain 1 (DEMOTE_1,
   SIP_DIS) and Domain 2 (DEMOTE_2, SYS_DIS) operate independently
2. **State Transitions (TEST 1.1)**: Verify all valid state transitions
   including sequential RMA path
3. **Debug/Test Isolation (Suite 3)**: Verify that feature control vectors
   properly isolate debug/test resources
4. **SEC_DIS Override (TEST 3.2 Phase D)**: Verify that SEC_DIS (representing SiP
   integrator emergency access) overrides domain-specific policies
5. **DEMOTE Security (Suite 2)**: Verify that DEMOTE_1/2 (volatile debug enable)
   cannot bypass two-domain security policies

The two-domain architecture ensures OCAH meets REQ-SEC-6 and REQ-SEC-7 while
maintaining compatibility with both simple single-chiplet deployments and
complex multi-chiplet SiP integrations.

TEST 3.6: sep_lcc_uvm_random_lc_state_test  [NEW]
------------------------------------------------------------------------
**Purpose**: Maximum-randomization feat_ctrl verification. Boots into a
random production-fused LC_STATE from eFuse, then exercises all LCC
controls with randomized order, timing, and combinations.

**Status**: ✅ PASS (2026-03-19) — 31 checks (seed=1, initial=RMA_SIP_1)

**Reusability**: NEW (0% — unique test concept, no Grendel equivalent)

**Sequence**: sep_lcc_uvm_random_lc_state_test_seq.sv
**Test Class**: sep_lcc_uvm_random_lc_state_test.sv

**Motivation**:
  All existing LCC tests constrain eFuse LC_STATE to TEST_DEV (0x0) and use
  W1S transitions to reach other states. This means no test verifies feat_ctrl
  on a chip that boots directly into PROD, PROD_END, RMA_SIP, etc. from OTP.
  Additionally, existing tests use fixed control sequences (DEMOTE_1 always
  before DEMOTE_2, LOCK_1 always before LOCK_2, SEC_DIS at fixed points).
  This test randomizes EVERYTHING to catch order-dependent bugs.

**Randomized Variables** (14 total):
  1. LC_STATE         — random from eFuse preload (weighted distribution)
  2. SIP_DIS/SYS_DIS  — random non-zero, differ (from eFuse preload)
  3. Non-critical LOCKS — 58 of 64 lock bits fully random (6 LCC-critical OFF)
  4. SECURE_TM        — random toggle at EVERY verification point
  5. DEMOTE order     — random: DEMOTE_1 first or DEMOTE_2 first
  6. DEMOTE_LOCK order — random: LOCK_1 first or LOCK_2 first
  7. SEC_DIS timing   — random: SEC_DIS before DEMOTE or DEMOTE before SEC_DIS
  8. TRANSIENT_RMA_EN — random from eFuse preload (may auto-transition to RMA)
  9. Inter-op delays  — random wait cycles (1-20) between operations
  10. Cold reset count — random (1-3) consecutive resets in consistency check
  11. W1S write data   — random 4-bit value (0x0-0xF) for transition fuzzing
  12. Token state      — random SIP/CHIPLET token match (on/off per iteration)
  13. PROD_DBG variant — random DEMOTE_1/DEMOTE_2/none when landing on PROD
  14. Fuzz iterations  — random 6-10 transition attempts per run

**Factory Override**: sep_efuse_item_lcc_random_state
  - LC_STATE: base class weighted distribution (NOT constrained to TEST_DEV)
    40% TEST_DEV, 30% PROD, 10% RMA_SIP_0, 5% RMA_SIP_1,
    5% RMA_CHIP_0, 5% RMA_CHIP_1, 3% PROD_END (INVALID excluded)
  - SIP_DIS != SYS_DIS, both non-zero
  - 6 LCC-critical LOCKS OFF, 58 other bits random (80/20 distribution)
    Bits OFF: TRANSIENT_RMA_EN wr/rd (4,5), SIP_DIS rd (7), SYS_DIS rd (9),
              RMA_SIP_TOKEN wr (10), RMA_CHIPLET_TOKEN wr (12)
    NOTE: LC_STATE bits (0,1) unconstrained — RTL ignores LOCKS for LC_STATE
  - TRANSIENT_RMA_EN: fully random (test adapts to auto-transitions)

**Test Steps** (variable cold resets depending on initial state + randomization):

  Phase A: Boot Verification                                       [0 resets]
    A.1: Read initial LC_STATE from shadow regs (random from eFuse preload)
    A.2: Verify feat_ctrl with SECURE_TM=0 (default) + CSR-vs-output
    A.3: Randomize SECURE_TM, random delay, verify feat_ctrl again

  Phase B: Upward Transitions + Random SECURE_TM + Delays         [0-3 resets]
    For each state reachable via W1S from the initial state:
    B.N: frontdoor_write_lc_state(target), random delay,
         randomize SECURE_TM, verify feat_ctrl + CSR-vs-output
    If landed on PROD (0x1): randomly set DEMOTE_1 or DEMOTE_2 → verify
    PROD_DBG feat_ctrl (W1S blocking tested in Phase F)
    Between transitions: cold reset to reload initial state from eFuse
    Reachable states per starting state:
      TEST_DEV (0x0) → PROD, RMA_SIP, PROD_END (3 targets)
      PROD     (0x1) → RMA_SIP (1 target)
      RMA_SIP  (0x2) → RMA_SIP_1, RMA_CHIPLET (2 targets)
      RMA_SIP  (0x3) → RMA_CHIPLET (1 target)
      RMA_CHIP (0x6) → RMA_CHIP_1 (1 target)
      RMA_CHIP (0x7), PROD_END (0x8) → terminal (0 targets, skip)

  Phase C: Random DEMOTE Order + DEMOTE_LOCK Order                 [2 resets]
    C.1: Sub-phase: Random DEMOTE order
      C.1.1: Baseline DEMOTE_1=0, DEMOTE_2=0
      C.1.2: Set RANDOM-first DEMOTE, random delay, random SECURE_TM, verify
      C.1.3: Set other DEMOTE, verify DEMOTE_1 priority
      C.1.4: Verify both DEMOTEs read back correctly
    C.2: Sub-phase: Random DEMOTE_LOCK order
      C.2.1: Set RANDOM-first LOCK
      C.2.2: Try locked DEMOTE write → blocked
      C.2.3: Write unlocked DEMOTE → succeeds (cross-pair isolation)
      C.2.4: Verify feat_ctrl with random SECURE_TM
      C.2.5: Set second LOCK, verify both locks active

  Phase D: SEC_DIS Random Timing                                   [1 reset]
    Random choice: SEC_DIS first or DEMOTE first
    Path A (SEC_DIS first):
      D.1: Activate SEC_DIS → verify override (all-1s)
      D.2: Set DEMOTE_1 → verify override persists
      D.3: Deactivate SEC_DIS → DEMOTE_1 effect appears
    Path B (DEMOTE first):
      D.1: Set DEMOTE_1 → verify feat_ctrl
      D.2: Activate SEC_DIS → verify override takes over
      D.3: Deactivate SEC_DIS → DEMOTE_1 re-emerges
    All steps: random SECURE_TM + random delays + CSR-vs-output

  Phase E: Multi-Reset Consistency                                  [1-3 resets]

    E.N: LC_STATE = initial, feat_ctrl = golden, CSR = output
    Tests eFuse → shadow → LCC pipeline determinism

  Phase F: Random State Transition Fuzzer                           [6-10 resets]
    Random 6-10 iterations, each:
    F.N: Cold reset → initial state
         Random write_data (0x0-0xF, covers valid + invalid destinations)
         Random token state (SIP match on/off, CHIPLET match on/off)
         Predict outcome via predict_lc_state_write_outcome()
         Execute raw W1S write to LC_STATE shadow register
         Read back actual state, verify matches prediction
         Random SECURE_TM, verify feat_ctrl at resulting state
    If landed on PROD (0x1): randomly set DEMOTE → PROD_DBG_1/2

Critical Note: security_disable Signal and LCC Testing Interaction
-------------------------------------------------------------------

**Background**:
  The SEP testbench uses a `security_disable` signal that overrides ALL lifecycle
  controller feature control logic. When `security_disable=1`, the LCC outputs
  0xFFFF_FFFF_FFFF_FFFF (all features enabled), completely bypassing LC_STATE-based
  restrictions.

**Current SEP Test Infrastructure** (as of 2026-02-10):
  - All AXI VIP-only tests (including eFuse tests) use `+SEP_SKIP_CPU_RUN` plusarg
  - `+SEP_SKIP_CPU_RUN` automatically sets `security_disable=1` (see sep_base_seq.sv)
  - Rationale: Without CPU firmware, inbound traffic filters would block AXI VIP access
  - Result: security_disable=1 allows tests to run but BREAKS all LCC feature control

**LCC Testing Requirement**:
  LCC tests MUST operate with `security_disable=0` to verify proper lifecycle-based
  feature control. However, setting `security_disable=0` requires inbound traffic
  filters to be properly configured to allow AXI VIP access to LCC registers.

**Recommended Workflow for LCC Tests** (TO BE IMPLEMENTED):

  Phase 1: Initial Setup (security_disable=1)
    1. Test starts with `security_disable=1` (bypass all filters)
    2. Use AXI VIP to program inbound traffic filters
    3. Configure filter to allow ONLY LCC register access from AXI VIP master
    4. Set up any other required system initialization

  Phase 2: LCC Testing (security_disable=0)
    5. Set `security_disable=0` via sep_misc_if.set_security_disable(1'b0)
    6. Verify filter allows LCC access (read/write LCC CSRs)
    7. Execute LCC test phases (state transitions, feature control, etc.)
    8. Verify all LC_STATE-based restrictions work correctly

  Phase 3: Cleanup (optional)
    9. Restore `security_disable=1` if needed for cleanup operations

**Implementation Details**:
  - Filter programming registers: TBD (depends on SEP inbound filter RTL)
  - Filter configuration: Allow AXI VIP master ID, LCC address range only
  - Verification: Read LCC CSR with security_disable=0 to confirm filter works

**Testbench Infrastructure Changes Required**:
  [ ] TODO: Implement filter programming sequence in sep_base_seq
