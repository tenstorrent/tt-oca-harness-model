# Key Manager model/test audit

## Scope and evidence

Audited model files: `include/key_manager.h`, `include/key_manager_base.h`,
`include/key_manager_register.h`, `include/km_mailbox.h`, `include/km_kpv.h`,
`include/km_firmware_handler.h`, and all five files under `src`.

Audited all test headers and all `key_manager_func001_test.cpp` through
`key_manager_func014_test.cpp`, `key_manager_test.cpp`, `testbench.cpp`,
`CMakeLists.txt`, `run_tests.sh`, and `doc/test_plan.adoc`.

No measured coverage percentage is claimed. The generic coverage target/gate
is wired (`CMakeLists.txt:170-188`, `run_tests.sh:69-72`), but no generated
coverage result was used.

## Behavior inventory

- SEP-visible regmodel mailbox: WDATA/WSEP/RDATA, live status, IRQ status/
  enable, overflow/underflow, and flush/control.
- Inbound/outbound 16-word FIFOs, separators, long-frame reassembly, IRQ level
  bits, sticky faults, firmware and SEP flush paths.
- Firmware boot/ready, CRC-8 header and CRC-32C payload validation, sequence
  tracking, response framing, recoverable/unrecoverable faults, and command
  dispatch.
- KPV 32-slot storage, one- to eight-slot key geometry, lock/write/use,
  random erase, validity, free-run search, opaque monotonically allocated
  handles, revoke and destination policy.
- Key generate/load/transfer/shred, dual XOR shares, HMAC/KMAC/AES/OTBN/ABR
  destinations, live demotion callback and OTP data.
- Active-low reset and emergency wipe; outgoing key delivery via eight TLM
  initiator sockets.
- SEP mailbox blocking transport is inherited from `regmodel::Memory`.

## Shortcut and integrity findings

1. **High — response integrity is never validated.**
   `test/src/key_manager_test.cpp:239-266` parses frame length and RESP_CMD
   fields but does not verify response header CRC-8 or payload CRC-32C.
   `mb_receive_frame` trusts the header length and reads that many words
   (`key_manager_test.cpp:205-236`) without checking the separator status.
   A corrupt response generated by the DUT can pass.

2. **High — expected CRC logic is copied from the implementation.**
   The request helper CRC algorithms at `test/src/key_manager_test.cpp:113-143`
   mirror `src/km_firmware_handler.cpp:713-742`. There are no independent
   published check vectors anchoring byte order/polynomial behavior, so the
   same error in both sides can pass framing tests.

3. **High — TLM failures are only warnings.**
   `test/src/key_manager_test.cpp:23-61` does not return response status or
   increment a failure count. All ordinary tests therefore assume transport
   success.

4. **High — dual-share test has a weak/incorrect oracle.**
   Production writes all SHARE0 words, then all SHARE1 words
   (`src/key_manager.cpp:255-260`). FUNC013 instead pairs
   `writes[w*2]` with `writes[w*2+1]` and merely ORs their XORs
   (`test/src/key_manager_func013_test.cpp:101-115`). Any mostly nonzero
   sequence passes; addresses, actual SHARE0/SHARE1 pairing, recovered key
   length/material, and commit address are not checked.

5. **High — downstream key-transfer failure is untested and ignored by model
   command handlers.** Recording stubs always return OK
   (`test/inc/key_manager_test.h:39-49`). Firmware calls `m_key_xfer` without
   checking its result for transfer and shred
   (`src/km_firmware_handler.cpp:564-575`, `590-598`). Tests cannot detect or
   define behavior for a destination error.

6. **Medium — claimed 17-word round-trip is not observed.**
   FUNC006 comments say the 17-word key “reads back intact,” but the test only
   checks successful load and nonzero handle
   (`test/src/key_manager_func006_test.cpp:124-144`). No transfer or direct
   comparison proves the second slot survives.

7. **Medium — helper-only coverage is mixed into the IP functional count.**
   `test/src/key_manager_func014_test.cpp:299-385` directly exercises
   `kpv_ctrl_t` and a local `km_kpv`. These do have assertions, but they prove
   C++ helper behavior, not that firmware commands reach those paths.

8. **Medium — outbound overflow behavior is only flag-checked.**
   `km_firmware_handler::push_message` ignores every `km_push_word` return
   (`src/km_firmware_handler.cpp:238-257`). FUNC014c only checks the overflow
   bit (`test/src/key_manager_func014_test.cpp:120-137`), not whether frames
   are atomic, truncated, recoverable, or resynchronized.

9. **No `#define private public` or test-only model hook was found.** Public
   OTP/demotion setters are integration interfaces; direct local-KPV cases are
   explicitly helper tests.

## Missing scenarios

- Independent CRC-8/CRC-32C known vectors, response CRC validation, malformed
  response separator/length/CRC, and resynchronization after truncation.
- Frame size exactly 16, 17, 256, and 257 words; split frames at every FIFO
  boundary; missing separator; multiple frames queued; separator on header or
  interior word; buffer overflow followed by a valid frame.
- Inbound/outbound simultaneous activity and IRQ transitions in the same delta;
  IRQ enable after pending; reset/wipe while a partial frame exists.
- Atomic behavior when outbound FIFO cannot fit a response.
- Destination socket command/address/data ordering, all addresses, exact XOR
  reconstruction, short-key tail randomization, OTBN 12-word layout, and all
  ABR destinations.
- Destination error/timeout propagation and whether locks are applied after a
  failed transfer.
- RAND failure in generation/masking/erase; deterministic DRBG injection for
  exact vectors.
- Handle 254/255/exhaustion, reset versus cold-domain OTP lock semantics, and
  live demotion changes at KDF invocation.
- MMIO command/address/response/unaligned/null pointer/length/byte-enable/
  streaming width/delay/debug/DMI/extension cases.

## Verdict

**Broad functional coverage with important oracle gaps.** Mailbox commands,
negative return codes, reset/wipe, and many key lifecycles are genuinely
transport-driven. Response integrity is not checked, the dual-share structural
test is not a valid oracle, and downstream TLM failures are neither injected
nor propagated.
